# EVE backend

GitHub Pages remains the frontend. A Cloudflare Worker handles EVE Authorization Code login with a confidential client, PKCE S256, signed-token validation, encrypted credentials, D1 snapshots, opaque dashboard sessions and scheduled refreshes every 10 minutes per pilot.

Only Fiofka (2124810474) and Decxus (2124815118) may enroll. Each pilot explicitly confirms sharing their skill total and queue on the public dashboard. Wallet, ship, location and industry data require the pilot's opaque dashboard bearer session. No EVE access or refresh tokens are returned to the frontend in backend mode.

## Deployment

GitHub environment **github-pages → Environment secrets** must contain:

- `CLOUDFLARE_API_TOKEN`: Account Workers Scripts Edit, D1 Edit, Account Settings Read, scoped to the intended account.
- `CLOUDFLARE_ACCOUNT_ID`: account ID, not zone ID or email.
- `EVE_CLIENT_SECRET`: secret from the EVE application whose public client ID is `a94f7ccbcc8b4b0d8f7fd90fec110d2b`.
- `PIPELINE_SECRET` (**one-time setup, you create it**): a long random string that signs the market pipeline's requests. Generate one, for example `openssl rand -base64 32`, and add it as an environment secret named `PIPELINE_SECRET` under **github-pages → Environment secrets**. The next deploy stores it in the Worker; the market pipeline reads the same secret from GitHub. Until it exists the pipeline keeps using its old fixed token (an HMAC of `EVE_CLIENT_SECRET`), which the Worker accepts only while it has no `PIPELINE_SECRET` and logs a warning for on every use. Once it is set, only signed requests work. To rotate it, change the GitHub secret and redeploy before the next pipeline run.

The check and backend deployment jobs explicitly select `github-pages`, so its environment secrets are available.

The Pages workflow validates the application, provisions/reuses `eve-journal` D1, applies migrations, deploys `eve-journal-api`, creates a persistent AES-256-GCM key in Cloudflare if absent, uploads the EVE client secret, verifies health, then publishes Pages with its public backend URL. It does not upgrade the account to a paid plan. Cloudflare product setup, limits, account permissions, and verification must permit Workers/D1 deployment.

The encryption key is never printed or committed. It is preserved across deployments. Do not manually delete or replace it while encrypted authorizations exist, or those authorizations will need to be reconnected.

**After deployment**, the GitHub workflow summary prints the actual Worker callback. Set that exact URL in EVE's developer application:

```
https://<actual-worker-host>.workers.dev/auth/callback
```

Then connect each pilot from Pages.

**New scopes need one reconnect.** The Worker also asks for `esi-markets.read_character_orders.v1`, `esi-contracts.read_character_contracts.v1`, `esi-killmails.read_killmails.v1`, `esi-characters.read_blueprints.v1`, `esi-planets.manage_planets.v1` and `esi-characters.read_standings.v1`. Tick all of them on the EVE application at developers.eveonline.com (client ID above) before the pilots reconnect, or the login is refused. They are optional on the Worker's side: a pilot who has not reconnected keeps syncing everything else, and the app shows “Needs permission” with a Reconnect button for the new data. A GitHub secret being present does not prove its value matches the EVE application; real EVE consent is required to verify the complete integration.

## Endpoints

- `GET /health`: database and configuration readiness; no secret values. Cheap and public.
- `GET /health/freshness`: public, ages in seconds only (no names, ids or locations): `market` (`metaAge`, `universeAge`, `hubs.count` and `hubs.oldestAge`), `activityAge`, and `pilots`, one `{pilot: 1|2, syncAge, error}` per connected pilot, numbered by position. `syncAge` is the time since the last fully successful sync. It answers 503 (with `problems` naming what is stale) when the market meta or a hub row is older than 3 hours, the kills sample older than 2 hours, or a connected pilot has not synced for an hour (a missing row counts as stale; a pilot whose grant EVE refused is flagged `error` but is not an outage, since only they can fix it). `.github/workflows/health.yml` calls it hourly and keeps one issue labelled `health` open while it fails.
- `GET /auth/start?pilot=<id>`: explicit sharing consent screen: the required public box, then three optional unticked boxes that set `pilots.share_wing` (2: ship, location, jobs, mining; 3, which needs the first, adds fit, blueprints and planets) and `pilots.share_alerts` (Discord alerts).
- `POST /auth/start`: CSRF-checked EVE OAuth redirect.
- `GET /auth/callback`: state-bound, single-use authorization-code exchange; redirects to Pages with an opaque session in the URL fragment, scrubbed immediately by the frontend.
- `GET /api/public/pilots`: whitelisted total SP and queue snapshots only.
- `GET /api/session`: own private snapshot; opaque bearer required.
- `POST /api/session/revoke`: ends the presented bearer session and nothing else. After a Reconnect the browser hands in the session it replaced, so old sessions don't linger for 30 days, and the pilot's other devices stay signed in.
- `POST /api/sync`: own ESI refresh, minimum one minute between successful updates.
- `GET /api/contract-items?id=<contract id>`: the items of one of the caller's own contracts (the id must be in the caller's stored contract list, else 404). One ESI request, made on demand and never by the cron; a courier contract has no items. Opaque bearer required; rate limited with `RATE_JOURNAL`.
- `GET /api/wing`: the pilots' wing summaries (skills, wallet, asset summary, with consent level 2 ship, location, 7-day trail, industry jobs and mining ledger, and with level 3 the current fit (`fit`: `{ship, items:[[type, flag, quantity]]}`), the hangar stacks (`stacks`), blueprints and planets) for pilots who share with their wingmate, plus the caller's own; opaque bearer required.
- `POST /api/sell-station`: body `{station: id|null}` (at most 1 KiB, the journal rate limiter); sets or clears the pickup station for the sell planner, stored as `sellStation` in the pilot's snapshot (written with `json_set`, so a running sync cannot lose it, and returned in the private payload). The id must be an NPC station (60,000,000 to 64,000,000) or a structure (above 1e12). Opaque bearer required.
- `POST /api/waypoints`: replaces the caller's in-game autopilot route with up to 40 systems (body at most 4 KiB); opaque bearer required and the pilot must be logged in to the game.
- `GET /api/market?v=2`: the market snapshot (item metadata, starter blueprints, prices per region scanned in the last 6 hours, and the cron's kills and jumps) with `universeVersion` naming the static universe document to merge in. Without a valid opaque bearer it serves the trade hubs only, since other regions show where the pilots fly. It sends a weak `ETag` built from the rows' timestamps and versions (and whether the caller is signed in), and answers a matching `If-None-Match` with 304 before reading any stored data. `Cache-Control` is `public, no-cache` (`private, no-cache` when signed in), so the browser always revalidates and Refresh is never answered from its own cache; the 304 keeps it cheap. Without `v=2` (pages from before the split) the gate map and static meta come inline, the shape the Worker always sent.
- `GET /api/market/universe?v=<version>`: the static universe document `{version, universe, meta}`: the gate map with NPC stations (region 1) and the meta that only changes with CCP's static data (`ores`, `combat`, `skills`). Public, holds no pilot data. Cached for a year when `v` is the current version, five minutes otherwise; `ETag` and 304 as above. The version is a hash of both parts and only changes when one of them does; an upload without static data keeps the last.
- `GET /api/market/regions`, `GET /api/market/survey`, `POST /api/market/ingest`: the market pipeline's reads and uploads, authorized by `PIPELINE_SECRET`: each request carries `X-Pipeline-Timestamp` (milliseconds) and `X-Pipeline-Signature`, a base64url HMAC-SHA256 over `timestamp|METHOD|path|base64url(sha256(body))`, valid for 5 minutes either side of the Worker's clock, so a captured request can't be replayed later, reused on another route or carry another body (`worker/pipeline-auth.js` is shared by both sides). Ingest takes only the pipeline's own regions (0, 1, 2, the five hubs, ESI region ids 10000001-10001000 and 11000001-11001000), checks the payload's shape and caps it at 1.9 MB measured in bytes. Without `PIPELINE_SECRET` the old fixed token is still accepted, with a warning in the logs.
- `GET /api/journal?since=<rev>[&prefs=1]`: goals (the wing's), the caller's own entries and, with `prefs=1`, the caller's own prefs changed after `rev`, oldest first, 500 per page (`more` says there is another), deletes as `record: null`; opaque bearer required.
- `POST /api/journal`: up to 40 changes `{kind, id, base, record|null}`. Each applies only if the stored rev still equals `base` (0 for a new record); otherwise the stored copy comes back in `conflicts`. Another pilot's entry is `denied`. Kind `pref` (migration 0005) holds a pilot's own setting under id `explored:<characterId>` or `haul:<characterId>`; only that pilot may write it (403 otherwise), it is never deleted, and it's validated per setting (at most 1000 scanned marks, 50 haul stops, 64 KB). Records are validated like a backup file and encrypted with `TOKEN_ENCRYPTION_KEY`. Deleted records stay as tombstones for 180 days. Disconnect keeps the journal.
- `POST /api/forget`: Delete my data. Waits for a running sync, has EVE revoke the grant, then deletes the caller's journal entries and preferences (`owner` = the pilot, and every `pref:*:<id>`), the pilot row and all their sessions. The wing's goals belong to both pilots and stay unless the body is `{"goals":true,"confirm":true}`, which turns them into tombstones the wingmate's device picks up (40 per call; `goalsLeft` says to call again). The newest journal row stays as an empty tombstone if it was theirs, because revs must never go backwards. The dashboard offers it as **Delete my data** beside Disconnect, behind two confirmations.
- `POST /api/disconnect`: waits for a running sync, requests EVE revocation of the newest refresh token (the reply's `revoked` says whether EVE confirmed it) and deletes stored enrollment, all that pilot's dashboard sessions and shared snapshot. If EVE's revocation service is unavailable, deletion still proceeds; account management can revoke the remote grant.

Rate limits use Cloudflare's Rate Limiting bindings (`ratelimits` in the generated Wrangler config), keyed by `CF-Connecting-IP`: `RATE_AUTH` 10 a minute for `POST /auth/start` (each one writes a D1 row), `RATE_MARKET` 60 for `/api/market`, `/api/market/universe` and `/health/freshness`, and `RATE_JOURNAL` 120 for `/api/journal` per session (the key is a hash of the bearer token). A refused request is a 429 with `Retry-After`. Without a binding (local runs, tests) they do nothing, and a binding that errors lets the request through. `POST /auth/start` bodies are capped at 4 KiB.

**Logs.** The deploy turns on Workers Logs (`head_sampling_rate` 1, automatic invocation logs off, so one event per request stays far inside the free plan's 200,000 a day). The Worker writes one JSON line per request (`{e:"req",route,method,status,ms}`; unknown paths log as `other`) and per cron run (`{e:"cron",job:"sync"|"sample"|"cleanup",pilot:"ok"|"failed"|"none",kills:"ok"|"failed",ms}`), plus `{e:"warn",what:"pipeline-legacy-token"}`. No tokens, ids, names, locations, query strings or addresses are ever logged. Read them under Workers & Pages, `eve-journal-api`, Logs.

**Discord alerts.** Optional. Set the `DISCORD_WEBHOOK_URL` secret to a Discord webhook (`https://discord.com/api/webhooks/<id>/<token>`: channel settings → Integrations → Webhooks → New webhook → Copy URL). With it, each cron run reads the stored snapshots of the pilots who ticked the alerts box on the consent page (`pilots.share_alerts = 1`, migration 0010, off by default; the channel is shared, so nobody is posted without agreeing, and reconnecting without the box turns it off) (no ESI calls) after its sync and posts up to 5 messages, one per new event: skill queue empty or ending within 24 h, an industry job ready, a market order outbid (checked against the stored market scan) or filled or expired, a contract accepted, completed or expiring within 24 h, a new loss. The `alerts` table (migration 0009, `key` primary key, `sent_at`) records what was sent so nothing repeats. A run reads the known keys with one `SELECT ... WHERE key IN (...)` per 90 candidates, so the number of queries does not grow with old events (D1's free plan allows 50 per invocation), then claims at most 5 new keys in one batch before posting; keys are released if Discord refuses a post, so it is retried on the next run. The daily cleanup deletes keys older than 30 days. Messages carry the pilot's name and item names only, never a system, station or region, and mentions are disabled. Without the secret (or with a URL that is not a Discord webhook) nothing runs. To set it up: add `DISCORD_WEBHOOK_URL` under **github-pages → Environment secrets** (like `PIPELINE_SECRET`); `scripts/deploy-backend.mjs` stores it in the Worker on the next deploy. Or set it by hand: `npx wrangler secret put DISCORD_WEBHOOK_URL`. To stop alerts, delete the Worker secret (a missing GitHub secret does not remove one already deployed).

**Cron.** Two triggers: every 5 minutes (a pilot sync, or the hourly kills sample) and `17 3 * * *` daily, which deletes expired sessions and login states, journal tombstones older than half a year (the newest row always stays) and alert keys older than 30 days. The Worker branches on `event.cron`. Expired sessions and states are refused where they are read, so they don't need cleaning more often. Migration 0008 indexes the columns these deletes and Delete my data use.

Opaque dashboard sessions expire 30 days after their last use; each day of use pushes the expiry forward. Scheduled refreshes run every 5 minutes and sync one pilot per run (the free plan allows 50 subrequests and 10 ms of CPU per invocation), so each pilot refreshes every 10 minutes. Once an hour, when ESI's `Expires` says both feeds have a new hour, a run samples `/universe/system_kills/` and `/universe/system_jumps/` (2 subrequests, sent with `If-None-Match`; a copy no newer than the last is not counted again) instead of syncing a pilot; the turn counter (`market_docs.turns`) then hands the skipped turn to the same pilot on the next run, so neither pilot always loses it. The sample updates the decayed 24 h / 7 day kill and 24 h jump history (`worker/activity.js`) and last hour's counts for high- and low-sec systems in `market_docs` `activity`. A failed feed keeps the history and is asked again after its `Retry-After`, or in 10 minutes. An upload from an older pipeline that still carries kill history replaces the cron's only if it is newer.

**Subrequest budget.** A pilot sync counts every request it makes (token refresh and key fetch included) and stops asking at `SYNC_LIMIT` (44), so with the up to 5 alert posts of the same cron run the total stays under the free plan's 50. The 13 core endpoints (with up to 19 more asset pages) run first. Then come orders, order history, contracts, killmails, blueprints, planets and standings, one after another from a round-robin cursor (`snapshot.cursor`): whatever the budget did not reach goes first on the next run. ESI caches most of these for an hour or more, so a run usually skips them. An order that leaves the live list waits in `snapshot.pendingOrders` (with `vanishedAt`) until the order history lists it, because ESI caches `orders/history/` for an hour: only then is it reported as filled or expired (cancelled ones are dropped), and one still unexplained after 24 h is dropped silently. This costs no extra request. Killmail details (the newest 10 recent killmails, public, read once and kept) and planet pins (one request per planet, oldest first) are read only while budget remains and continue on later runs. The snapshot keeps compact forms only: orders (100), history of the last 30 days (60), contracts (open ones first, 100), losses (25), blueprints grouped by type (400), planets (12) with a pin summary, standings (120), and the ship's own items for the current fit (never the full asset list). **Hangar stacks (`operations.stacks`).** While the asset pages are read, the Worker also keeps the packaged stacks in the item hangar (`location_flag` `Hangar`) of the station the pilot is docked at now (`location.station_id`, else `structure_id`) and of the pickup station in `snapshot.sellStation`: `{value: {[station]: [[type, quantity]]}, fetched}`, biggest first, at most 300 types per station (every wanted station gets a list, empty or not). Singletons (assembled ships, containers, other assembled items) and blueprint copies are left out; the ship's cargo is already in `fit`. The permission is the assets scope. No extra request: the same pages. Stored stacks stand on an unchanged (304) or unexpired assets answer, but only while they cover every wanted station: a new dock or pickup station makes the next sync read the assets in full (no ETag). A page newer than page 1 discards the whole read, stacks included. At consent level 3 the wingmate gets `stacks` like the fit; `sellStation` is never sent to the wingmate.
A test counts subrequests per run in the worst case.

Pilot syncs follow ESI's caching rules. Each endpoint's `ETag` and `Expires` are stored in the snapshot (`esi`, never sent to the browser): an endpoint whose `Expires` has not passed is not asked and keeps its stored value; after it, the request carries `If-None-Match` and a 304 keeps the stored value without parsing anything. Assets are read page by page, and a 304 on page 1 keeps the stored summary without reading the other pages (all pages share one cache entry); a page with a different `Last-Modified` from page 1 keeps the previous summary. A 429 (ESI's rate limit) or 420 (its error limit) holds that pilot's ESI calls, token refresh included, until `Retry-After` (or `X-ESI-Error-Limit-Reset`, or a minute; `pilots.esi_after`, migration 0007) and keeps the last good data. When `X-ESI-Error-Limit-Remain` or `X-Ratelimit-Remaining` drops below 20, the sync sends no more requests and keeps the last data for the rest (endpoints go four at a time so this can take effect). Routes are unversioned with `X-Compatibility-Date: 2025-12-16` (`ESI_COMPAT`). Disconnect waits for a running sync, then revokes the newest refresh token. Encrypted refresh tokens remain server-side for scheduled updates until disconnected or revoked. D1 stores private snapshots, protected by the API session checks; the credentials themselves are additionally encrypted with AES-GCM. Each encrypted blob (`v:2`) binds the row it belongs to (`pilot:<id>`, `goal:<id>`, `entry:<id>`, `state:<hash>`) as additional data, so a blob copied into another row does not decrypt; older `v:1` blobs still decrypt and are rewritten as `v:2` the next time their row is saved (credentials at the next token refresh, journal records at their next edit).

When EVE answers a refresh with `invalid_grant`, the Worker records it (`grant_revoked_at`, migration 0005) and stops asking EVE for that pilot, scheduled turns included, until the pilot reconnects. A 429 from EVE login holds refreshes until its `Retry-After` (at most an hour; `refresh_after`). The OAuth callback clears both.

Only the configured Pages origin can issue browser API requests. OAuth consent/callback cookies are first-party, HttpOnly, Secure, SameSite=Lax. No cross-site third-party cookie is required by Pages. EVE responses and secrets are not logged by the Worker; observability is disabled in deployment configuration.

## Plan: moving to a custom domain

Not implemented; a plan for when the wing owns a domain. Today the page is on `matheusfiorin.github.io` and the API on `*.workers.dev`. Those are two different sites (both suffixes are on the Public Suffix List), so:

- The dashboard session can't be a cookie. A cookie from `workers.dev` on a `fetch` from `github.io` is a third-party cookie, which Safari blocks and other browsers are phasing out. So the opaque session is a bearer token in `localStorage`, readable by any script on the page, and Safari's 7-day rule deletes it.
- `github.io` is a shared origin. Every GitHub Pages project of this account runs on `matheusfiorin.github.io` and can read this app's `localStorage` (sessions and the journal). The CSP limits what this page runs, not what the account's other pages do.

The fix is to serve both halves from one registrable domain, say `app.<domain>` for the page and `api.<domain>` for the Worker:

1. **DNS and hosting.** Add the zone to Cloudflare and serve the page from Cloudflare too (Workers static assets or Cloudflare Pages, the same files the Pages workflow copies into `_site/`). Safari caps server-set cookies at 7 days when the API's IP address doesn't share the first half of the page's (its defence against CNAME cloaking), so `app.` on GitHub Pages' addresses and `api.` on Cloudflare's would lose the cookie as fast as `localStorage`. GitHub Pages with a custom domain (a `CNAME` file in the artifact, Enforce HTTPS) works for everything else but not for that. Give the Worker a custom domain `api.<domain>` (a `routes` entry with `custom_domain: true` in `scripts/deploy-backend.mjs`) and keep `workers_dev` on until the move is done.
2. **Configuration.** `FRONTEND_URL=https://app.<domain>/`, the frontend's `backendUrl=https://api.<domain>` (`scripts/configure-frontend.mjs`), `connect-src` for `https://api.<domain>` in `index.html` (and drop `https://*.workers.dev` afterwards), and the EVE application's callback URL `https://api.<domain>/auth/callback`.
3. **Session cookie.** `app.` and `api.` are the same site, so `/auth/callback` can set the session as `Set-Cookie: __Host-eve_session=…; Path=/; Secure; HttpOnly; SameSite=Lax` on `api.<domain>` and redirect to the page without a token in the fragment. The browser sends it on `fetch(…, {credentials:'include'})`; CORS answers with `Access-Control-Allow-Origin: https://app.<domain>` and `Access-Control-Allow-Credentials: true`. Page scripts can no longer read the session, Safari's 7-day rule for script-writable storage doesn't apply to an HttpOnly cookie set by a same-site server on the same network (step 1), and Lax still keeps it off cross-site requests. One cookie per pilot (`__Host-eve_session_<id>`), or one cookie listing both of this browser's pilots, keeps the two-pilot model. State-changing requests keep the exact-Origin check, plus `Sec-Fetch-Site: same-site` or a custom request header, as CSRF defence. Expiry stays server-side (30 days from last use); `Max-Age` mirrors it.
4. **A non-shared origin.** `app.<domain>` holds only this app, so its `localStorage` (the journal, drafts) is no longer readable by other GitHub Pages projects.
5. **Migration.** For a release, accept both the cookie and the bearer header; on load, a page that still holds a bearer session trades it once for a cookie (`POST /api/session/upgrade`) and deletes it from `localStorage`. The journal doesn't move between origins by itself: sync it to the backend (or export a backup) on the old address, then open the new one and connect. Keep the old Pages site up for a while with a notice that links to the new address, then remove the bearer path and `*.workers.dev` from `connect-src`.

## Verification

Worker unit tests use SQLite to exercise real migrations and query behavior, generated signed tokens, encrypted-at-rest assertions, public/private data separation, OAuth state/cookie binding and replay rejection, token rotation, session expiration, CORS, deletion and scheduler behavior. Frontend tests cover opaque sessions and shared snapshots alongside existing browser-only fallback behavior. `npm run check` syntax-checks the Worker; there is no Wrangler dry-run build. Actual Cloudflare deployment and EVE consent must be verified separately.
